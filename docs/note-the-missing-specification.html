The specification that is not there Why the section numbers in the code point at nothing

Around a hundred and twenty comments in this codebase cite a specification by section — spec §4, spec §11, spec §16 — and several quote it directly. There is no such file, in this repository or anywhere else. This note exists so that whoever goes looking for it stops looking.

What happened Established 17 August 2026

A specification numbered DBBS/UM/KRAM/01 Rev B, dated 10 August 2026, was written up early in the project from U&M's concept deck and the conversations around it. It was drafted inside a working session and never saved to a file. When the session ended, so did the document.

The project log recorded it as “truncated at ~50k characters, cutting off the tail of §19 and all of §20 Open items”, and treated it for a week as something the client still owed us. Neither is right. U&M never had it — the DBBS/ prefix is our own numbering, so it was ours to hold — and there is no fuller copy anywhere to ask for.

What the deck is, and is not Checked, not assumed

docs/source/concept-deck.pptx is the client's brief and is genuinely the requirements document: nineteen slides covering objectives, dashboard features, a five-row scope of work, the MD's KPIs, and the screens they want. It is not the specification. It carries no speaker notes, embeds no documents, and contains no numbered sections at all — so no citation in this codebase can be resolved against it.

Verified by reading the file rather than by opening it: nineteen slides, zero notes slides, zero embedded parts, zero section-style references anywhere in the XML.

If you need to know what a section said

The citations mostly carry the sentence with them. Searching the codebase for the section number returns the claim it was making, in context, next to the code that implements it:

grep -rn "§11" --include=*.sql --include=*.ts .

That is weaker than the document would have been, but it is not nothing — and unlike the document, it cannot drift away from the build without somebody noticing.

What was lost, honestly

Less than the log implied. The concept deck has been audited slide by slide (log §9, 15 August); that audit found three things claimed and not built, all of which were then built. The deck's own §18, Immediate Followups, is the closest thing to the “open items” section that was supposedly missing — and it lists D-minus article-wise, article-wise capacity per day with average manpower, and manpower and overtime tracking. All three are now either built or formally requested.

What is genuinely gone is a numbered document to check the build against. The log carries the decisions and the reasoning, and is kept current in a way a specification would not have been.

Why it is not being reconstructed

It could be — roughly a hundred and twenty quoted citations is enough to rebuild it section by section. It is deliberately not being done, for two reasons.

A specification derived from the build cannot then be used to audit the build. It would read as an independent check and be nothing of the kind, which is the exact failure this project keeps naming: something that looks like verification and cannot fail.

And the work it would displace is real — driving the hosted client in a browser, and the two screens missing from the user guide. Both are on the go-live list. A reconstructed specification is not.

If U&M ever need a document to sign off, the right answer is a short scope note written for that purpose — not a reconstruction dressed up as the original.
